# BoxShot

原生 macOS 截图与录屏工具，一个菜单栏图标搞定 14 个动作：区域截图、滚动截图、OCR、二维码、屏幕测量、区域/全屏录制、摄像头录制、贴图。

零第三方依赖——截图走 ScreenCaptureKit，识别走 Vision，热键走 Carbon，编码走 AVFoundation。

- 当前版本：**1.0.28**
- 作者：ccvi1223 · ccvi1223@qq.com
- 工程最低版本：`.macOS(.v14)`（`Package.swift`）
- 常驻形态：`LSUIElement = true`，只在菜单栏，不占 Dock

截图浮层的工具条按参考图重排成**一行图标**（选择 → 箭头 → 画笔 → 矩形 → 椭圆 → 直线 → 文字 → 马克笔 → 马赛克 → 模糊 → 测距 → 取色），颜色和粗细收进左边那颗"当前颜色"圆点的弹出层。1.0.11 起 **`⋯` 菜单取消**：里面的 OCR / 解码 / 贴图 三个动作全部摊到工具条上，"复制到剪贴板"那条本来就和工具条上的 📋 重复，一并去掉。之前 6 色 + 3 档粗细平铺，工具条能撑到 1300pt宽。工具条始终贴着截图框（优先放下方，放不下放上方，上下都放不下压进框内底部），框改完尺寸会跟着重新落位 —— 见下文「工具条落位」。

### 颜色面板：贴在工具条下面，6 个颜色

点工具条上那颗「当前颜色」圆点，会在工具条**下方**展开一块面板：**6 个圆形色块**（黄 `#F8CE43` / 绿 `#62C563` / 蓝 `#3887FB` / 红 `#EB4259` / 橙 `#F3933D` / 紫 `#BD3DDD`，`OverlayEditorController.colorPalette`，直径 **18.72pt**（26 的 80% 再 ×90%，用户口径 1.0.10「小 20%」→ 1.0.11「再小 10%」）、圆角取半径）+ 3 档粗细。色值是照用户给的色卡逐像素取的，自检里连顺序一起钉住。以前是 `NSPopover`，弹在圆点旁边、压住截图内容，位置还跟着圆点跑；现在是一块独立浮层，贴工具条下沿 8pt，横向与工具条左对齐（下面放不下就翻到工具条上方）。

### 字号：面板最右端一个 6 档下拉（1.0.23）

颜色面板最右边隔一条竖线放一个 `NSPopUpButton`：**20 / 24 / 30 / 40 / 52 / 68 pt** 六档
（`OverlayEditorController.fontSizeOptions`）。默认 30 —— 加控件之前浮层里写死的就是
`30 * pixelScale`，档位必须包含它，不然老用户的第一段字会突然变大变小，而且下拉会显示成
"没选中"。

三件事必须分清：

- **下拉显示的是点，形状里存的是图像像素**（`shape.fontSize`）。落成形状时乘 `pixelScale`，
  回显时除回去；所以 2x 屏上选「30 pt」写出来的是 60px 的字 —— 在图里看仍是 30pt 那么粗。
- **只对文字生效**。选着矩形改字号既不该动它、也不该白压一个撤销点，所以
  `applyToSelected(color:lineWidth:fontSize:)` 先算出"改完长什么样"，跟原来一模一样就直接返回。
- **正在输入时改字号是实时的**：`setLiveFontSize` 同时改形状字号和编辑器字号，不压撤销点
  （落盘时随整段编辑一起算一个点），字立刻变大变小 —— 和"输入时就看到最终效果"是同一件事。

下拉的回显取**最近**的一档而不是精确相等：形状字号是像素，换成点再换回来带浮点误差
（60px → 30.0000001pt），精确匹配会一档都对不上，用户改完字号看着像没生效。

色块一路缩下来（26 → 20.8 → 18.72），面板高度从 48 → 37 → **35pt**。两个连带项不能漏：分隔线（`colorPanelDividerHeight = 18`）和那 3 颗粗细按钮 —— 后者原来是 27×32 硬编码，比色块高，面板就被它撑住不跟着缩（而且 32 高塞进 21 高的行里会被裁成"一条虚线"）。现在它的高 = 色块直径、宽 = 直径 × 1.3，示意线也按这个尺寸重画。诊断脚本里那颗合成点击的坐标是按 `swatchSide` 算的，改直径不用动它。

**工具条与颜色面板的底色（1.0.16 用户口径）**：「两个工具条变成圆角矩形框，底色为不透明的灰黑色」。以前两个容器都是 `NSVisualEffectView(.hudWindow)` 毛玻璃，截图内容（晚霞之类的暖色）从底下透出来，图标看着发脏。现在换成实心 `NSView` + `layer.backgroundColor = toolbarBackgroundColor`（灰黑 `white: 0.13`，两处共用一个常量），圆角不变。注意 `NSVisualEffectView` 无论 `state` 怎么调都会画一层材质，要实底必须换 `NSView`。

### 编辑器色板 = 截图工具条色卡（1.0.16）

编辑窗口的色板以前另写一份 `[red, blue, yellow, green, white, black]`，跟工具条的 6 色色卡对不上。现在统一收进 `RGBColor.palette`（黄绿蓝红橙紫，顺序 = 用户色卡），工具条与编辑器引用同一份常量，自检断言两处 hex 完全一致防漂移。加色只改 `RGBColor.palette` 这一处。

### 步骤标注 / 截图美化 / OCR 表格（1.0.16）

- **步骤标注**（编辑窗口）：点一下画布放一个圆底数字，序号**不存进形状**，渲染时按 shapes 数组顺序数（`EditorRenderer.stepNumber`），SwiftUI 预览与 CG 导出共用同一份函数——删掉中间一步，后面的自动补号，也就不需要"重置序号"按钮。圆底半径 26 / 字号 28，颜色跟当前画笔色。浮层（原位编辑）同样支持，但工具条按钮只在编辑窗口。
- **截图美化**：`BeautifyOptions` 挂在文档上（nil = 关）。**底图永远不动**：渲染时先铺背景（9 个纯色预设 + 3 个渐变预设），再填一个不透明圆角矩形投影（阴影 blur 24 / 下移 8，固定不做 UI），把底图裁进同一个圆角矩形。编辑器画布同步预览：手势坐标整体减 padding，适配缩放按"底图 + 2×padding"算。🔴 渲染里 CoreText 翻转用的 `canvasHeight` 必须传**底图高度**（美化时标注空间原点已平移到 padding 处），传整张画布高会把文字画飞。
- **OCR 表格 → Markdown**：Vision 只跑一次（`recognizeObservations`），行聚类沿用 `groupedRows`（格子带横向范围）；分列靠**列缝检测**——收集多列行里单元格之间的空白带、横向求交，出现在 ≥ 一半多列行里的才算列边界（空单元格天然跳过）。结构太散（行 <2 / 多列行不占半 / 列 >10）就放弃返回 nil，别硬拼。结果窗检测到表格时多一个「复制为 Markdown」按钮。

两个坑都出在同一件事上 —— **`NSStackView` 只认 `intrinsicContentSize`**：

- 色块是"空标题 + `layer.backgroundColor` 上色"的 `NSButton`，没有任何内容能算尺寸，于是宽高都是 0，整排色块被压成 0 宽 —— 面板看着是**空的**（`fittingSize` 也只有那几个有图标的粗细按钮那么宽）。修法：给色块 / 粗细 / 分隔线各加显式的宽高约束。
- 同一颗「当前颜色」圆点更早就中过这个招：它在工具条里，尺寸一直是 0，用户根本**看不见**有这个东西可点。1.0.10 一起补上约束。

另外非 key 窗口里的 `NSButton` 默认 `acceptsFirstMouse = false`，点颜色要连点两次才生效，所以色块用的是 `FirstMouseButton`（一律接受首击），面板本身也做成能成为 key 的窗口。

### 高亮：聚光点亮，不是染色

用户把工具条上原来那个「裁剪」位置要走了，换成**高亮**。第一版做成了"荧光笔染色"（`multiply` + 38% alpha 铺一层颜色），用户随后附样张纠正：他要的是**聚光**——拖出的矩形**一个像素都不动**（文字仍是最深的黑、底色仍是原色），把图里其余部分压暗 60%。

量他样张得到的口径：框外 `(102,102,102)`、框内纯白、框内文字最暗 18 —— 也就是"框内完全没被覆盖"。所以现在的实现是：

```swift
ctx.addRect(canvas)            // 整幅画布
ctx.addRect(spot)              // 要点亮的那块
ctx.clip(using: .evenOdd)      // 只剩"矩形外面"
ctx.setFillColor(CGColor(gray: 0, alpha: 0.6))
ctx.fill(canvas)
```

三个坑记在这里：

- **不要用 `shape.color`**：聚光没有"颜色"这个概念，跟当前选的颜色无关，恒定用黑色压暗。改动前那版是按颜色染，才会出现"选白色 = 什么都看不见"。
- **alpha 0.6 是从样张量出来的**，不是随手定的（白底 → 102 灰）。自检里钉了这条。
- SwiftUI 侧（独立编辑窗口）同样的效果必须**包一层 `drawLayer`**：`GraphicsContext` 是值类型，直接在 `context` 上 `clip` 会把后面所有标注一起裁掉（症状是"画了高亮，别的标注全不见了"）。

它和「马克笔」也不是一回事 —— 马克笔是**半透明的笔画**（跟着手走），高亮是**一块面**（拉框，只点亮这块）。

### 工具条尺寸：倍率开关 + 只缩「当前颜色」圆点

工具条的尺寸全部从一个倍率推出来（`OverlayEditorController.toolbarScale`）：图标字号 / 圆角 /
间距 / 内边距 / 分隔线高度 / 容器圆角。**当前值 1.0 = 原尺寸**，实测 **514×32pt**
（原来是 523×32，少的 9pt 就是颜色圆点从 30 缩到 21）。

用户 1.0.11 的原话是「工具条那个控制颜色的小圆按钮缩小 30%」。第一版我把整个工具条按
0.7 缩了 —— 他说的是**那颗圆点**。所以现在：

```swift
static let toolbarScale: CGFloat = 1.0            // 工具条原样
static let colorAnchorSide: CGFloat = 30 * 0.7    // 只有这颗圆点缩 30% → 21pt
```

🔴 **不要给工具条按钮加显式宽高约束**：这类"空标题 + 图片"的按钮，内禀尺寸来自图片本身，
给约束反而会把它钉死。而且原来那句 `frame = 40×38` **从来没生效过**
（`NSStackView` 只认 `intrinsicContentSize`，真实按钮约 24×32）—— 如果照着 40×38 去算
"缩 30%"，会得出 596×39，比原尺寸还大。**改比例之前先量基准**：
诊断浮层启动时会打一行 `[BoxShot][toolbar] frame=`，直接读，不要靠截图目测。

例外是「当前颜色」圆点：它只有 `layer.backgroundColor`、没有图片，内禀尺寸是 0，
显式约束不能省（省了会被压成 0 宽、整个圆点看不见）。

### 工具条落位：下 → 上 → 框内底部，间距 10pt

三步口径（`OverlayEditorController.toolbarOrigin(selection:toolbarSize:visible:)`，纯函数，自检里有 9 条断言）：

| 顺序 | 条件 | 落点 |
| --- | --- | --- |
| ① | 框下方放得下（默认） | 工具条**底边**比框底边低 **10pt** |
| ② | 下方顶到可见区底边 | 工具条**底边**比框顶边高 **10pt** |
| ③ | 上下都不够（框高顶满整屏） | **压进框内底部居中**，底边距框底 10pt；框比工具条还矮时竖直居中 |

横向一律按框中线居中，再夹进可见区。

两个坑：间距以前是 8pt（用户要求 10pt）；「放上方」那支以前写的是 `selectionFrame.maxY + barHeight + 8` —— `barHeight`（30）是图内那条刻度带的高度，跟工具条毫无关系，于是往上放时会凭空多出 30pt 空隙，看着像"跑偏了"。

③ 这条基本只在框很高时才出现，真机上很难手动复现，所以顺手加了 `--show-overlay-tall`（用一个 520×1020 的合成框开浮层）专门看它。


**出厂没有任何全局热键**（1.0.1 起）。所有动作都要在「设置 → 快捷键」里自己录一遍，不录就是没有——见下文「快捷键」一节。

## 截图只走 ScreenCaptureKit

`SCScreenshotManager.captureImage` 单帧截图，`CGDisplayCreateImage` / `CGWindowListCreateImage` 全工程零调用。`CGWindowListCopyWindowInfo` 仍然用，但**只枚举窗口几何**做「智能识别窗口」的高亮——它不读窗口内容，因此不依赖屏幕录制授权。

多显示器只做**单屏**：选区窗口和全屏截图都锁定 `NSEvent.mouseLocation` 命中的那块屏。跨屏拼接没有实现。

### 三套坐标系，别混

| 坐标系 | 原点 | 谁在用 |
| --- | --- | --- |
| CGWindowList / NSEvent 全局坐标 | 主屏左上角，y 向下 | 窗口枚举、鼠标位置 |
| `SCStreamConfiguration.sourceRect` | 目标显示器左上角，y 向下 | 截图请求 |
| AppKit | 主屏左下角，y 向上 | 所有窗口/视图布局 |

全局 → 显示器局部是减去该屏 `CGDisplayBounds().origin`；AppKit ← 全局是 `y = 主屏高 - rect.maxY`。像素换算不在截图侧做：`captureImage` 直接吃点的 `sourceRect`、吐像素尺寸的 `CGImage`，点→像素的换算只发生在 UI 层（标注那一步）。

## 框完就截：选区阶段没有"调整态"了

1.0.10 起，拖完**松开鼠标就是截图**。之前要再「单击选区内」或按 ⏎ 确认一次，用户看到那行提示的反应是「我以为还没截」，多一步还容易以为卡住了。

- 阈值照旧：宽或高 < 8pt 视为误触，留在选区模式，不产生一张 3×5 的废图。
- **代价是选区阶段的八向手柄、方向键微调、Shift 约束正方形一起下线**（它们都挂在"调整态"上）。改尺寸这件事本来就在截完的浮层里做，那里有真手柄、能拖框、能扩出去从整屏原图取内容，比在遮罩上调更完整。
- 提示文案跟着改成「拖动框选区域 · 松手即截图 · Esc 或右键取消」，拖拽中显示「W × H · 松手即截图」。
- 验收用 `--dragtest`：合成 10 步 `leftMouseDragged` 后再 `leftMouseUp`，判定「遮罩自己收掉 + 浮层按拖出来的框打开」。实测拖 560×420，浮层 `frame=(420, 387, 560, 420)`（AppKit 左下原点，`1107-720=387` 对得上）。

## 参数接进来却没人用：窗口截图等于普通截图

`startRegionShot(copyDirectly:windowPickMode:pipeline:)` 里的 `windowPickMode` **一直是只进不出**——签名收了这个参数，函数体里没人读，于是「窗口截图」和「开始截图」行为完全一样；除非用户碰巧在设置里开了「窗口高亮」，否则点窗口根本没有可点的目标，看起来就是"这个动作没生效"。

现在：`highlightWindows: windowPickMode || prefs.value.windowHighlight`，且窗口模式下**关掉十字线**（要的是点窗口，不是拉框）。验收用 `--windowtest`：合成一次单击，检查浮层框明显小于全屏（实测拿到 `(0, 58, 855, 1015)`，正是当时那个前台窗口）。

## 窗口截图：框不能动，也得能改大小

窗口截图走的是另一条路：它不重新截整屏，而是用 `SCContentFilter(desktopIndependentWindow:)` 单独抓那个窗口（被遮住也能抓到干净内容）。1.0.9 之前它**不带整屏原图**，于是两个毛病一起冒：

1. `canResize = fullDisplay != nil` → 窗口截图的框**拖不动**（用户："也可以调整大小"）；
2. 浮层窗口的尺寸是"窗口框 + 上下留白"（上面还要放 30pt 的刻度带）。框一高就顶出屏幕，AppKit 在 orderFront 时会调 `constrainFrameRect(_:to:)` 把它推回来 —— **整张图跟着下移**，和真实窗口错位（用户："自动捕捉大窗口时，截图框不要移动"）。

现在也给窗口截图一份 `FullDisplay`：**裁切基准**是「窗口图 + 窗口框」（`commitResize` 会 intersection 到这个框，所以只能往里收、扩不出去），**浮层范围**是整块屏幕（`panelFrameAppKit`）。浮层铺满屏就不会再被 constrain 推走。

实测（`--windowtest`）：窗口框 `(0,58,855,1015)`、浮层 `(0,0,1710,1107)` 与屏幕完全一致；拖右下角手柄向内 120pt 后变成 `(0,178,735,895)`。

> 教训：加参数先搜一遍它在函数体里出现过几次。`swift build` 不会为「未使用的形参」报警（它本来也允许），这种洞只有端到端跑一遍才露出来。


## 滚动截图：听用户的滚轮，不合成事件

全工程没有一个 `CGEvent`。做法是装全局 + 本地两个 `scrollWheel` 监听（滚轮事件不需要辅助功能授权），用户自己滚，程序负责抓帧。

- 🔴 **质量门别跟"窗口内均值"比（1.0.26）**：分离度原来算的是 `base±7px` 窗口里的平均 mad。白底多的真实网页里，附近每个偏移都"挺像"（实测均值 4.4~6.5），于是一个 **mad=0（逐像素完全相等）的完美解**也会因为"没拉开 8 的差距"被拒 —— 用户看到的就是"滚得再慢也老提示这一帧没对上"，连挂 3 次再演成"内容跳变已跳过一段"。现在分离度跟**全局粗搜中位数**比（`baseline`），并新增门 ⓪：逐像素完美 + 画面有纹理就直接认（纯色页面纹理≈0，仍然拒绝，不放开 1.0.5 那道"瞎拼"防线）。离线复现 192 例（整数 / 亚像素 / 带固定表头），旧门误杀 61 例且带表头 15 例，改后 0 例。
- **「页面没动」不再算失败**：滚到头 / 光标压在不可滚区域时两帧逐像素一样，以前照样走"没对上"，连挂 3 次还重置基准。现在先做 `isNearlyIdentical` 判断，静默提示"页面没动（可能到头了），继续滚动"。
- **只拼「停下来」的帧（1.0.15）**：滚动途中不抓帧，停稳 250ms 后再抓。途中帧带平滑滚动的亚像素相位 + 运动残影，像素差天然超标会被质量门拒掉 —— 用户看到的就是「明明滚得不快却老提示没对上」；更糟的是连挂 3 帧会重置基准，拿运动中的帧当基准，后面拼出来全是错位。代价是快速滑动会留下缺口（状态条会提示），宁缺勿错。
- 🔴 **触摸板必须按距离中途抓帧（1.0.25）**：上面的"只拼停稳帧"对鼠标滚轮成立，对触摸板不成立 —— 两指一划惯性动辄滚出一两屏，惯性事件把去抖一直往后推（用户看到"半天不动"），真停稳时页面已离基准一整屏开外，**两帧零重叠，对齐必然失败**，连挂 3 次就是"内容跳变已跳过一段"。修法：精确 delta（触摸板）按累计滚动距离抓帧，每滚 `max(48pt, 区域高×0.4)` 抓一帧（相邻帧 ≥60% 重叠）；运动帧对不上**不计入失败数**（亚像素/重绘是惯性常态，不是内容跳变），静默跳过等停稳帧补。鼠标滚轮一格一点，停稳再抓本来就够，路径原样不动。
- **尾部去抖 250ms**：最后一次滚轮事件后 250ms 才抓帧，触控板惯性刚结束那一下还可能带亚像素相位，宁多等不早抓。
- **忙时不丢帧**：抓帧期间又停稳触发，置 `pendingGrab`，当前帧回来后补抓一次。
- 每帧都是重新走一遍 `SCScreenshotManager`，不是 `SCStream` 连续流。

### 缩略图：强制打开、不能关闭、180 × 700、方角

滚动截图一开始就把缩略图面板建出来（`showPreview()`），跟着整个流程存在：无边框、没有标题栏、没有关闭按钮，也不接收鼠标事件（`ignoresMouseEvents`）—— 鼠标从它上面滚过去时滚轮事件直接落到下面的页面，不会把用户"卡"在缩略图里。标题实时显示累计像素尺寸。

**尺寸 180 × 700（1.0.28）**：用户口径从 180×600 → 200×700，当天又改回 **180×700** —— 高度要够（长图一进来就缩成细条），宽度还是 180 顺眼。`previewWidth`（缩略图专用低分辨率画布）必须跟面板同宽，否则位图会被拉伸发虚；自检里有一条断言把两者锁死，改一个忘一个会红。

**方角（1.0.28）**：用户「缩略图窗去掉圆角」。`cornerRadius` 10 → 0，1pt 描边留着 —— 面板是深色的，下面压着任意网页内容，全靠这圈边分界。

**铺满后整幅缩放（1.0.25）**：长图没铺满缩略图框时按宽度铺满（原行为）；一旦铺满（高度超出框），改成整幅缩到框内 —— 高度贴框、宽度按比例缩小并水平居中，越长图宽越窄，整幅长图一眼看全，不再滚动预览（`previewDocumentSize`，自检 3 条）。

落位是纯几何函数 `ScrollCaptureController.previewOrigin(region:visible:size:)`（可以脱离界面喂数字验，自检里有四条）：优先贴截图框**右侧**，右边放不下换**左侧**，竖直方向顶边对齐框顶边并夹进可见区。**不能被自己的取景框拍到**是硬约束 —— 重合了每帧都会把缩略图录进画面（同下面第 1 条坑）。左右上下都塞不下（截图框几乎占满整屏宽）时只能退到屏幕右边缘，这种框本来也不该配滚动截图。

### 开始滚动前可以调选区大小（1.0.28）

用户口径：**「只要还没开始滚动，截图框的大小都可以调整大小。滚动开始就不能调整了。」**

之前拖完框就直接开抓，没有调整的机会。现在会话一开始是**可调整阶段**：选区四周各有 8 颗白色手柄（四角 + 四边中点），拖动任意一颗改大小；第一次**真实滚轮位移**（单次 > 2pt）就锁死，手柄和拖动一起失效。这里没有"开始"按钮 —— 滚动本身就是开始信号。阈值用 2 而不是 1：触控板放上去常有 0.1~0.5 的抖动，用 1 会在用户还没动的时候就把框锁掉。

几个必须做对的地方：

- 🔴 **手柄必须画在选区外面。** 面板正好盖在选区上，画在内侧会被抓进基准帧（见上面第 1 个坑）。所以面板留白从 2pt 提到 14pt（`panelInset` = 边框 2 + 手柄 9 + 余量），手柄中心在选区边外 6pt。
- 🔴 **边框不能再用 `bounds.width - 2` 画。** 那是"面板边缘减 2"的老写法，留白一变成 14，画出来的蓝框比真实选区大一圈 12pt —— 用户看到的框和截到的内容对不上。四条边框必须贴着 `regionRect` 算。
- **拖动中不抓帧，松手才重置基准。** 一次拖动会触发几十次 `mouseDragged`，每次都整屏抓一遍会卡成一帧一卡。所以拖动只改 `region` + 重排三块面板（取景框 / 工具条 / 缩略图），`mouseUp` 才清空画布重新抓基准帧。
- 🔴 **异步抓帧有两个竞态**：① 帧回来时选区可能已经改了，尺寸对不上 → 用 `regionVersion` 版本号作废这一帧；② 松手时正好有一帧在飞，`grabFrame` 的 `!isBusy` 守卫会把重开吞掉 → 记一个 `pendingRebaseline`，等这帧回来再补基准，否则就没有基准帧了。

选区下限 80 × 80，并且整体夹进屏幕可见区（`clampRegion`，纯几何，自检 5 条）。可调整阶段状态条会说「拖边框调大小 · 开始滚动后自动锁定」。

### 工具条顺序：贴图 → 复制 → 保存 → 完成 → 取消（1.0.28）

用户口径：**「滚动截图的工具条图标顺序改为：贴图，复制，保存，完成，取消」**。原来是「✕ 取消 / ✓ 完成 / 分隔线 / 📌 贴图 / ⬇ 保存 / 📄 复制」—— 决策键打头、输出动作在右，手指要先横跨半个工具条。现在按**输出在前、决策在后**排成一条流水线，那根分隔线也一并去掉（同一条流水线的五步，不该分两组）。图钉的 tag 仍是 4、取消 2、完成 3、保存 5、复制 6，`buttonTag` 按标题查表，顺序变了不影响动作。

### 状态提示条：黑字压黑底，看不见（1.0.28）

用户截图：选区上方那条「已捕获 1 段，滚动页面继续」黑得几乎读不出字。

根因是 1.0.27 统一配色时的连带遗漏：`ScrollFrameView.draw` 里文字色换成了 `ToolbarTheme.foreground`（纯黑），而胶囊底还留着写死的 `NSColor.black.withAlphaComponent(0.78)` —— 于是黑字压黑底。现在底色也走主题（`#E6E6E6` 实底 + 黑字），并补一圈 `ToolbarTheme.divider` 的 1pt 描边：浅灰压在浅色网页上会糊成一片，得靠这圈边把胶囊勾出来。

**教训**：改「前景色」时必须同时扫一遍同一处**写死的背景色**。这类"半改"在自检里查不出来（颜色对不对只有人眼能判），只能靠把配色收进 `ToolbarTheme` 一个来源来防再犯 —— 这也是 1.0.27 建那个文件的初衷。

### 取景框绝不能在选区里画东西

取景框是一圈**画在选区外侧**的边框 + 选区上方一条状态带（`ScrollFrameView`），选区内部全透明。原因见下面第 1 条坑：指望 ScreenCaptureKit 把自家窗口排除掉是靠不住的。顺带的好处是用户能看着页面滚，不至于对着一帧冻结的图猜「到底截没截上」。已捕获段数和本段位移写在状态带上。

拼接（`Stitch.swift`）是纯函数，可以脱离界面跑，`--selftest` 里有逐像素断言。

1.0.5 重写后的三段式（1.0.4 那版拼出来「不连续、全错」）：

| 阶段 | 做什么 | 为什么 |
| --- | --- | --- |
| 粗搜 | 240 宽灰度，步长 2 行 | 只负责「大概滚了多少」，毫秒级扫完几百个候选 |
| 选窗口 | 取粗搜前 10 名 + 离 hint 最近的那个 | 等距内容有多个「完美」候选，正确周期可能排在后面 |
| 精修 | 每个窗口在原分辨率（宽 = 图宽）逐像素搜 | 1 像素精度靠这一步，粗搜的亚像素得分纯属噪声 |
| 择优 | 多个解都逐像素相等时取离 hint 最近 | 等距列表 / 表格靠这条才不跳周期 |

质量门两条，缺一就拒绝本帧（宁可不拼也不瞎拼）：

- **`mad ≤ 6`**（门 ①）/ **`mad ≤ 20` 且分离度 ≥ 12**（门 ②，1.0.15 新增）：门 ② 给亚像素停靠留余量 —— 触控板 / 平滑滚动停下的位置经常带小数（比如 137.4px），两帧各自带着抗锯齿重采样渲染，正确 d 的 mad 会被抬到 10~20、跟相邻 d 拉不出深坑，这不是「对错了」而是「对上了但带着半像素误差」。自检里有对应断言（`smoothPage` 造 137.4px 分数偏移，要求对上且落在 137…138）。
- **分离度 ≥ 8**：最优解的 mad 要明显低于窗口内其他候选的均值。纯色 / 空白画面里每个候选都是 0，最优解毫无意义 —— 判「分离度」跟画面亮不亮、有没有细节都无关。1.0.4 用 `texture >= 1 || mad <= 1.5` 兜底，纯色恰好走后者，把「什么都不像」当成「完美匹配」拼了进去。
- **相邻窗口的解合并时留 mad 更小的那个**（1.0.15）：窗口按 center 升序扫，低窗口可能先交出一个「还行但不是最优」的解，把真解当重复项丢掉 —— 实测伪解 d=136（mad 14.7）先进队，真解 d=137（mad 0）被去重逻辑吃掉，第一段就差一个像素。

**不用特征匹配**：滚动对齐只在一维上，暴力搜几百个候选就是毫秒级，鲁棒性反而比特征点稳（网页上重复的图标 / 文字会让特征匹配乱跳）。

固定表头 / 底栏在两帧里位置不变，会把最优解往 d≈0 拖，所以比较时跳过当前帧顶部 10% + 底部 4%（跳过量会被压到重叠区的 1/4 以内 —— 重叠只剩几十行时按帧高算的 50 行比重叠区还大，会把比较区削成负数，明明能对上却返回 nil）。搜索上界按「至少留 5% 重叠」算，不是写死 8%。两帧宽度差 1px 会累积错位，先统一到 `min(topW, bottomW)`；重叠区取上方帧的内容（下方帧可能带输入法候选框或滚动条闪烁）。横向滚动把图顺时针转 90° 复用同一套算法，拼完再转回来。

### 四个坑（都写进了注释）

1. **取景框被拍进了画面**（用户看到「不连续」的真凶）。取景框浮在选区正上方，框里还画着上一次的拼接预览 → 每帧截到的都是上一帧的预览。
   **`SCContentFilter(display:excludingWindows:)` 救不了**：我们的面板在 `.floating` / `.statusBar` 层，而 `SCShareableContent.windows` 基本只列 layer-0 的普通窗口，按 pid 过滤出来是空数组，excluding 成了空操作。诊断办法：把 `accumulated` 存盘看一眼 —— 第一帧顶部赫然烧着状态胶囊，就是自己的框被拍进去了。
   现在的做法是**取景框不在选区里画任何东西**（四条实心边框条 + 上方状态带 + 8 颗调整手柄，全都落在选区外），不依赖那个 API。1.0.28 加手柄时就是踩在这条上：第一版把手柄画在选区**内侧**，面板留白只有 2pt，结果基准帧的四个角上烧着 8 个白方块 —— 于是把面板留白从 2pt 提到 14pt（`ScrollFrameView.panelInset`），手柄挪到边框外面，自检里有一条断言逐颗验「整颗在选区外」。
2. **`CGContext` 位图缓冲是 top-down**。绘制坐标系是左下原点，但缓冲区第 0 行就是图像最上面一行，`CGImage.cropping(to:)` 的 y 也从顶部算。曾经「顺手翻转成 top-down」，等于两张图同时上下颠倒，正偏移 d 在数学上永远对不上（只有 `d = -offset` 成立），粗搜全落随机水平。
3. **`append` 的新高度是「已有高度 + offset」**，不是「top + bottom − 重叠」。写成后者等于把 bottom 的重叠部分又加了一遍：1173 行的页面拼出 2330 行，内容全是重复的。
4. **一帧对不上就永久卡死**。原来失败时只留一句提示、基准不动 —— 用户接着往下滚只会离基准更远，于是每一帧都失败，表现就是「只截了一次，之后怎么滚都不动」。现在：失败先反着对一次（判「往回滚」），连续 3 次失败就换基准从当前画面接着截（状态条上明说中间可能有缺口）。


## 标注渲染的三次翻车

三条都是「画了但看不见」级别的问题，注释里都留着原文：

1. **马赛克用直线路径裁剪 = 零面积**。`clip` 只认闭合区域，直线裁剪之后什么都画不出来。现在按「拖拽起止点围成的矩形」clip。
2. **`ctx.scaleBy` 方向反了**。标注存的是图像像素坐标，回到视图坐标要乘 `1/pixelScale`；曾经乘成 `pixelScale`，结果标注整体放大 4 倍画到图像区域外。
3. **画底图的顺序反了**。必须先在不翻转的标准空间画底图（那里 `CGImage` 方向才是正的），再 `translate + scaleBy(1, -1)` 翻成左上原点画标注。顺序反了底图整体上下颠倒——形状位置对、内容倒，特别迷惑。

标注一律存**图像像素坐标**，不存视图坐标。编辑器有缩放，保存/复制/贴图用的却是原始分辨率，坐标换算只该发生一次。撤销/重做是整数组快照（`undoStack: [[AnnotationShape]]`），没有上限也没有 NSUndoManager。

## 窗口录制：区域录制 + 点选窗口自动填框

用户口径（1.0.27）：**「窗口录制跟区域录制的功能要一样，只是窗口自动补抓了」**。所以它不是"只录某个窗口的图层"，而是：

1. 出选区遮罩，**强制窗口高亮**（和「窗口截图」同一套点选，无十字线、带整屏底图兜底）；
2. 点中窗口 → 把窗口框换算成显示器局部选区（`ScreenCapture.displayLocalRect(fromAppKit:)`）；
3. 之后**完全走区域录制**：虚线取景框、工具条、全屏、重选区域、系统声音、麦克风、摄像头取景框，一个都不少。

- **工具条可以拖着挪走**（用户 1.0.27 口径："截图时，工具条可以拖动调整位置"）。工具条常横在选区正下方，正好压住要标注的内容。实现是给容器换成 `DraggableToolbarContainer`（`mouseDown` 里调 `window.performDrag(with:)`）—— 🔴 无边框 `NSPanel` 默认**不响应拖动**（没标题栏，`isMovableByWindowBackground` 也是 false），不自己接事件就拖不动。按钮会吃掉自己的 `mouseDown`，所以只有按在按钮间隙 / 内边距上才拖，点按钮不打架。拖过的位置在本次浮层里保持；换一张截图按 `toolbarOrigin` 重新算回默认位置（新浮层不该继承旧位置）。
- 🔴 **刻意没用 `SCContentFilter(desktopIndependentWindow:)`**。窗口滤镜能跟着窗口走、不怕遮挡，但它只给那一个窗口的像素 —— 摄像头浮窗、系统声音、全屏/重选这些区域录制的能力就都没法一致了，跟用户要的"功能一样"直接冲突。代价是录制期间窗口被拖走，画面会跟着"内容跑出框"（同区域录制）。
- 窗口录制模式下如果用户改成拉框选区，按区域录制处理（`didConfirmRegion` 里的 `.recordWindow` 分支），不让这次操作白费。
- **菜单入口在「区域录制」正下方**（用户 1.0.27 指定）：区域 → 窗口 → 全屏 → 摄像头，三种"录哪儿"连成一组。原先「摄像头录制必须紧贴全屏录制下方」的约定随之让位 —— 它俩是同一条链路，挨着才讲得通。

## 录屏：会话起点必须是第一帧视频的 PTS

`SCStream` + `AVAssetWriter`，H.264，码率 = `像素宽 × 像素高 × fps × 系数`（高 0.12 / 中 0.06 / 低 0.03 bpp）。

关键时序：`startSession(atSourceTime:)` 统一取**第一帧视频的 PTS**，音频帧在会话开始前到达就直接丢。丢零点几秒开头的声音，比留一个 PTS 早于会话起点的坏文件强。

声音是三选一互斥枚举（无 / 系统声 / 麦克风），**没有系统声 + 麦克风同时录的路径**。默认麦克风。没有「暂停过 + 无摄像头」时 `sampleBuffer` 零拷贝直通到 writer。

### 系统声音「回响」的根因：两路音频串到了一条轨（1.0.27）

症状是成片里同一段声音出现两遍（一次数字直采，一次像绕了一圈回来），听感就是回响。根子在音频回调被**两路共用**：

| 来路 | 回调 | 以前 |
|---|---|---|
| `SCStream` `.audio`（系统声音） | `stream(_:didOutputSampleBuffer:of:)` | 和麦克风共用一个 `handleAudioBuffer` |
| `AVCaptureAudioDataOutput`（麦克风） | `captureOutput(_:didOutput:from:)` | 同上 |

那个共用 handler 只按「`systemAudioInput` 有没有」决定往哪条轨 append。于是只要有系统音频轨在（录音时选了系统声音），晚到的麦克风缓冲就被塞进**系统音频轨** —— 同一段声音两条来路叠一层，就是回响。

同一个坑还有两个帮凶：

- `captureSession` 一个字段被**麦克风和摄像头（画中画）两路**赋值。谁后赋谁赢，先建的那个 session 再也没人 `stopRunning()`，一直跑着继续往 writer 上 append（表现：收工后麦克风/摄像头指示灯还亮；严重时同一时间轴两段音频叠加）。现在拆成 `micSession` / `cameraSession`，`teardownPipeline` 两个都停。
- `beginMicCapture()` 是**权限回调里**异步执行的。用户点完"允许"时这路录制可能早就停了、或者已经切到系统声音模式，那时再开麦就会往当前那一路灌。现在开头有 `guard writer != nil, micAudioInput != nil, micSession == nil`。

现在两路各管各的（`handleSystemAudio` / `handleMicAudio`），共用部分只剩 `audioBuffer(_:)`（暂停期间丢帧 + 恢复后减掉暂停空隙）。另外 `config.captureMicrophone = false`（macOS 15+）显式关掉 SCK 自带的麦克风采集，别再偷偷多抓一路。

「最多一条音频轨」被写成可断言的事实（`RecordAudioSource.tracks`），自检 4 条盯着 —— 将来真要加"系统 + 麦克风"混录，是改这里并被断言拦住，而不是让成片里悄悄多一层回声。

排查工具：录制启动时会打一行 `[BoxShot] 音频路由：capturesAudio=… 系统轨=… 麦克风轨=…`，两条轨同时是 1 就一定有问题。

### 摄像头取景框：所见即所得，不在编码端合成

右下角那个圆形 / 圆角矩形小窗（`CameraBubble`）是一个**真的屏幕窗口**，进视频的方式就是被 ScreenCaptureKit 拍到，编码端**不再**合成画中画。

原因很硬：想让「窗口在屏幕上可见、但不进录像」只有一条路 —— 把它塞进 `SCContentFilter.excludingWindows`。可我们的面板在 `.floating` / `.statusBar` 层，而 `SCShareableContent.windows` 基本只列 layer-0 普通窗口，压根拿不到它，excluding 是空操作（滚动截图取景框那次已经踩过一模一样的坑，见上文）。所以选「屏幕上什么样，视频里就什么样」：

- 圆 / 圆角矩形**单击画面**（或右键）切换，✕ 或工具条上的 📷 关掉，录制中也能开关（只是显示 / 隐藏一个窗口，视频管线完全不动）；
- 预览层自拍镜像，不然用户看到自己的手是反的；
- 因为不再合成，`AVAssetWriterInputPixelBufferAdaptor` 那条合成路径现在只服务「暂停后重编时间戳」。


录制时把自己家的浮条 / 工具条 / 贴图放进 `excludingWindows`，它们不会进画面。过滤条件按 **pid** 认自己，不按 `bundleIdentifier`：裸二进制调试时后者是 nil，过滤结果恒为空，等于没排除。

🔴 **但按 pid 一刀切会把「本意要录进去」的窗口一起排掉** —— 摄像头取景框就在同一个进程里。1.0.9 的用户反馈「录制生成的视频没有摄像头的影像」就是这条：取景框明明在屏幕上，却被自己的排除名单干掉了。现在 `Recorder` 多一个白名单：

```swift
var keepVisibleWindowNumbers: Set<Int> = []   // 工具条把取景框的 windowNumber 塞进来
let ownWindows = content.windows.filter {
    $0.owningApplication?.processID == ownPID && !keep.contains(Int($0.windowID))
}
```

并且每次开录都留一行 `lastExclusionReport`（`排除 N 个 · 保留 M 个 · 本进程窗口 K 个`）—— 这类问题只能靠这三个数字判断错在哪一侧，光看画面分不清是「没上屏」还是「被排掉了」。实测：`排除 0 个 · 保留 1 个`，成片抽帧右下角能看到人像。

### 三个把「点录制」直接干掉的坑

1. 🔴 **`AVVideoAverageBitRateKey` 不能放在 `outputSettings` 顶层**。那是老写法，macOS 26 的 `AVAssetWriterInput` 当场抛
   `NSInvalidArgumentException: Output settings dictionary contains one or more invalid keys: AverageBitRate`，
   而这是 **ObjC 异常，Swift 的 `try/catch` 接不住** —— 进程直接 SIGABRT。
   表现就是「点一下录制，应用从菜单栏消失」，一行日志都留不下。码率必须塞进
   `AVVideoCompressionPropertiesKey` 字典里（`AVVideoExpectedSourceFrameRateKey` 一并放进去）。
   这个 bug 活了三个版本，因为它是**必崩**而不是偶发：`Recorder.swift` 里从前没有一行代码跑到过。
2. **H.264 要求宽高是偶数**：选区是随手拖的，501×301 之类很常见，像素宽高统一向下取偶。
3. **麦克风授权只问一次**：`requestMicThenCapture()` 以前被连着写了两遍，于是每次录音建两个
   `AVCaptureSession`，第二个把第一个顶掉、第一个继续失控地占着麦克风，两路音频还同时往同一个
   writer input 上 append。

启动是**异步**的（`SCStream` 还要等系统把显示器/窗口列表给回来），所以工具条在按钮已变成"停止"、
计时器已经在走之后才可能收到失败。失败必须把界面退回去（`startingUp` 标记），否则用户看到的是
"正在录"，实际一个字节都没写。麦克风/摄像头缺失走 **`onWarning`** 而不是 `onError` —— 少一路声音
不该把好好的录制退回去。

## 选区调整：拖出来先别截，等确认

两段式：拖出范围 → `.adjusting` 阶段（八向手柄 / 方向键 / ⇧ 正方形）→ **在选区内单击一下**（或回车）才真正截图。

- 🔴 **不要双击**。1.0.4 要求双击确认，用户明确否掉了 —— 单击最顺手。判定就一条：按下到松开的位移 ≤ 2pt 算单击（`RegionSelector.OverlayView.isTap`），超过就是"拖动选区"，手柄拖拽更不受影响。
- **Esc 不是出口**。用户要求「截图没完成，或没主动点击取消，都不能结束截图」：选区遮罩里 Esc 只撤当前选区，标注浮层里 Esc 只撤"正在画的那一笔"或待确认的裁剪，都不结束流程。要退出选区就**右键**（画面上常驻提示「拖动框选区域 · 右键取消」），要关标注浮层就点 ✕。在此之前 Esc 会直接把整条流程/整张标好的图丢掉。
- 截图浮层（标注工具栏那个）**点框外不会关闭**。原来点一下外面就把浮层关了、标注一起丢，属于"没主动取消却被结束"。
- `finish()` 里**不能当场把遮罩窗口和视图释放掉** —— 它在 `OverlayView.mouseUp` 的栈上被调用，当场析构就是 use-after-free（崩溃栈 `objc_release ← -[__NSArrayM dealloc] ← objc_autoreleasePoolPop`，随机闪退）。现在的做法是先 `orderOut`，强引用交给下一轮 runloop 再放。同理，所有程序化创建的 `NSPanel` 都设了 `isReleasedWhenClosed = false`，否则 `close()` 和 ARC 会抢着释放同一个窗口。

- **状态机是显式的**（`idle / dragging / adjusting / movingSelection / resizing`），而不是靠一堆布尔变量互相猜。滚动截图、录屏、OCR 共用同一个遮罩，改一处全部受益。
- **手柄容差 9pt**：太小点不中，太大又会把手柄拖拽变成移动选区。
- **移动时夹在屏内**（`bounds` 是这块屏幕），否则选区会跑到看不见的地方，截图请求直接失败。
- 方向键微调 **1px / ⇧ 10px**：对着像素做人眼校准，步长必须是 1。

## 标注阶段随时改截图框：整屏原图 + 关掉重开

截图框不是截完就钉死了。浮层的八个手柄都能拖，拖的时候画虚线预览框 + 框外压暗，松手才提交。

- **得多存一张整屏原图**。要把框拉大，扩出去的那块内容只有两个来源：重新截屏（会把我们自己的浮层拍进去，内容也可能已经变了）或者截屏那一刻的整屏原图。所以区域截图会额外抓一张 `SCDisplay` 全图，跟着浮层一起传下去。
- **窗口铺满整块屏幕**。窗口要是只比图大一圈，往外拖的预览框会被窗口裁掉，看着像没反应。现在图像面板 = 整个显示器，其余部分透明（透过去就是桌面，观感跟参考图一致）。
- **提交时"关掉自己、按新尺寸重开"**，和裁剪同一套：从整屏原图按新框 `cropping`，标注按 `旧原点 − 新原点` 平移，然后重开。坐标换算永远只有一套，不会留下半个旧状态。
- 🔴 **y 轴必须翻**：AppKit 是左下原点，整屏原图是左上原点，`pixelRect(for:displayFrame:pixelScale:)` 里 `y = 显示框.maxY − 框.maxY`。弄反了就是"拖框裁出屏幕另一头的内容"，而且自检看得见 —— 这条有断言。
- 🔴 **"关掉自己"必须推到下一轮 runloop**：`commitResize` 是被自己视图的 `mouseUp` 调起来的，而 `close()` 会让 AppModel 清掉 `overlayEditor` —— 控制器只剩视图里那个 `unowned` 引用，于是**在方法执行途中被释放**，下一行读 `self.model` 就是野指针（`RegionSelector.finish()` 当初崩四次同款）。做法：要用的值（裁好的图 / 新框 / 平移后的标注）先全部取成局部量 → `orderOut` 把旧框当场藏起来（别让用户看见弹回旧尺寸）→ `DispatchQueue.main.async` 里再 `close()` + 重开，并用局部强引用把控制器活到闭包结束。
- 「Retina 缩小到 1x」开着时文档是 1x、整屏原图是 2x，两边倍率对不上，标注没法平移，这时候直接不允许改尺寸（宁可不给，也不给错位的结果）。

## 裁剪：不改文档，改成"重开一个"

裁剪没有原地改 `EditorDocument.baseImage`。原因：浮层的 `imageRect`、手柄、面板尺寸都是 `init` 时定死的，原地改会留下半个旧状态（布局按旧尺寸、标注按新尺寸）。

做法是 `croppedResult(to:)` 产出一份「裁好的底图 + 平移到新原点的标注」，然后**关掉当前浮层 / 窗口，按新尺寸重开一个**：

- 坐标换算永远只有一套（`imageRect` ↔ 图像像素），不会出现两套并存；
- 被裁掉的标注直接丢弃（`displayBounds` 与裁剪区不相交），不会留下"看不见但还在"的幽灵；
- 重开期间 `suppressAutosave`，否则自动保存会把**裁剪前**的图落盘一份。

## 浮层并存与完成即关（1.0.24）

**连续截图时浮层并存，都是活的。** 以前 `AppModel.openOverlayEditor` 每次 `overlayEditor = controller` 直接覆盖：旧 controller 被释放，但窗口还留在屏幕上（AppKit 保留在屏窗口）—— 按钮动作全是 `[weak self]`（self 已 nil）点了没反应、Esc 监听同样失效，contentView 持的 `unowned controller` 点图像区还会崩。这就是"连续截几张，旧窗口变成僵尸、关不掉只能退应用"的根因。现在 `overlayEditors: [OverlayEditorController]` 数组保活全部并存浮层，`onClose` 按身份摘除；`overlayEditor` 仍指向最新一个（诊断/自检用）。

**「完成后直接关闭截图窗口」**（设置 → 截图）：OCR / 解码 QR / 贴图 / 复制 / 下载 任一动作**成功**后自动收掉浮层。**滚动截图同理**：工具条上的贴图 / 保存 / 复制成功后收掉整个会话（取景框、工具条、缩略图、滚轮监听全撤），✕ 和 ✓ 不受这个开关影响。细节：

- 延迟 0.5s 再关，让 flashStatus 那句"已复制 / 已保存"来得及看，也顺手绕开"在自己按钮回调里同步拆自己窗口"的老坑（`asyncAfter` 闭包强持有 self）；
- **失败不关**：QR 没认出来、保存编码失败、保存面板点了取消，浮层都留着；
- OCR 没有回调可等，触发即视为交出（识别失败走全局报错）；`close()` 加了 `didClose` 防二次执行。

## 工具条「编辑」按钮：连同标注一起进独立编辑器（1.0.27）

用户口径：**「在工具条加上 编辑 按钮，点击进入编辑器，同时关闭截图窗」**。位置在他截图上指的那一格 —— 高亮与 OCR 之间，图标 `square.and.pencil`（别跟画笔 `pencil.tip`、马克笔 `highlighter` 撞），快捷键 ⌘E。

三个实现要点：

- **交的是 `baseImage + shapes`，不是压平的 `rendered()`。** `EditorWindowController.show(image:shapes:)` 本来就收标注，两边坐标又都是图像像素坐标，原样搬过去就行。压平等于交出一张"撕不下来的成品"，进去连撤销都回不去。
- 交出去之前先 `contentView?.commitTextEditing()`：正在输入的那行字还是视图里的草稿，不 commit 就不在 shapes 里，会凭空少一句。
- **无条件关浮层**，跟设置里「完成后直接关闭截图窗口」那个开关无关（那个管 OCR / 解码 / 贴图 / 复制 / 下载）。内容已经整份交给编辑窗口，浮层再留着就是两张一样的图。关闭本身推到下一轮 runloop —— `close()` 会触发 `onClose` 把 controller 从 `overlayEditors` 里摘掉，同步关就等于在自己方法执行到一半时把自己释放了（裁剪重开那次踩过同型坑）。

顺带把 `editorController` 改成 `editorControllers: [EditorWindowController]`：以前只有滚动截图结果会开编辑窗口，一份引用够用；现在每张截图都能点进去，覆盖引用 = 旧编辑窗口留在屏上没人管，跟 1.0.24 修的浮层僵尸窗口是同一个形状。诊断入口仍按"最近一个"取（只读计算属性）。

## 编辑标注窗口：能拖边框改大小（1.0.28）

用户口径：**「编辑标注窗口能不能拖拉边框改变窗口大小啊。」** —— 之前不能，因为 `EditorWindowController.init` 里的 `styleMask` 只有 `[.titled, .closable, .miniaturizable]`，没有 `.resizable`，四边全是死的。加上就完事，但有两件事得一起做对：

- 🔴 **`contentMinSize` 一定会被 `NSHostingView` 盖掉。** 在 `init` 里设 `window.contentMinSize = 640×420` 是无效的：`window.contentView = NSHostingView(rootView:)` 那一拍，SwiftUI 会按自己的 fitting 尺寸重算窗口的最小尺寸，实测能一路拖到 **596×286** —— 工具条压成一团、画布只剩一条缝。修法两层：装完 `contentView` **再设一次** `contentMinSize`（绿灯的缩放语义也靠它），再加 `windowWillResize(_:to:)` 在 delegate 层硬夹 —— 这一层是最后一道，拖边框必过。
- **`collectionBehavior = [.fullScreenNone]`**：这个窗口是"改完就走"的临时工作区，绿灯保留 zoom 就够了；进全屏会把横向工具条撑得很怪。

窗口大小只影响显示，不动数据：`fitScale` 由 `GeometryReader` 的实测尺寸算，标注坐标一直存在图像像素空间，拉大拉小之后位置和字号自动跟着换算（`pixelFontSize` / `pointFontSize`）。每次 `show()` 仍按图片尺寸重算并居中，所以"拖好的大小"不会跨截图保留 —— 这是有意的，每张图比例不一样。

诊断：`--editorbar`（或 `/tmp/boxshot-editorbar.trigger`）用一张 900×600 合成渐变图直接开编辑窗口。正路要「截图 → 浮层 → 点编辑」，验一次得先有截屏权限、还得点中那颗按钮。

## 工具条配色：四条用 ToolbarTheme，编辑窗口不动（1.0.27 / 1.0.28）

用户口径两句话：

1. **「所有工具条 底色改为 #E6E6E6，工具条的图标颜色改为黑色，颜色图标除外。」**
2. 紧接着又补一句：**「编辑标注窗口的工具条不用改底色，保持原来的就行了。」**

所以 `Sources/BoxShot/Capture/ToolbarTheme.swift` 覆盖的是**四条悬浮工具条** —— 截图浮层、录制工具条、录制时长 HUD、滚动截图工具条。**编辑窗口（`EditorView`）不在范围内**，它继续用 SwiftUI 的 `controlBackgroundColor` 跟着窗口外观走。别顺手给它也套上主题。

三个坑：

- 🔴 **不能交给 `.labelColor`。** 底色是写死的浅灰，前景跟着系统外观翻的话，一开深色模式就是白底白图。所以 `ToolbarTheme.foreground = .black` 写死，同时给容器设 `appearance = .aqua` —— 分隔线、`NSPopUpButton`、禁用态这些以后加的控件才都按浅色解析，比逐个手写前景色彻底。
- 🔴 **不显式设 `contentTintColor` = AppKit 会把模板图标画成 50% 黑（#737373）。** 不是黑，是灰。悬浮工具条里的 `NSButton` 都是 `isBordered = false` + 模板 `NSImage`，`contentTintColor = nil` 时按半透明黑绘制。滚动截图与录制两条工具条第一版就是这个毛病，肉眼在截图里能看出"图标发灰"。
- **颜色圆点只改描边，不改填充**：`swatchBorder` 从白 0.75 改成半透明黑 0.35（白边在浅底上等于没有），圆点本身必须显示用户真正选中的红 / 黄 / 蓝 —— 这就是"颜色图标除外"。语义色同样保留：取消红、完成绿、录制红、暂停黄。

诊断：`--recordbar`（或 `/tmp/boxshot-recordbar.trigger`）直接出「全屏录制」工具条，**不真开录** —— 录制工具条只有真录制时才上屏，而真录制会写视频、还要等好几秒，验配色根本没法逐版对比。

## 录制暂停：不能真停流

（GIF 已移除，1.0.12 —— 它是全应用唯一的内存事故点：帧序列逐帧收 `CGImage` 全程常驻内存，600 帧 × 1000px 上限能到 1.8GB。配置里遗留的 `"gif"` 在解码时迁回 `.mp4`，**不能**直接删 enum 项完事：`decodeIfPresent` 碰到未知值抛错，整份设置会回退出厂，快捷键、保存目录全没。`RecordFileFormat.from(legacyRaw:)` 就是这个迁移口，自检里有整包解码的断言。）

- **暂停不能真停流**：停了恢复时首帧要等几百毫秒，writer 的会话起点也要重算。做法是照旧收帧全部丢弃，恢复后把这段空隙从后续 PTS 里减掉（`pausedTotal`）。
- 🔴 **时间轴补偿必须用 PTS 算，不能用墙钟**：SCStream 的 PTS 来自主机时钟，两者刻度不同，混用会得出离谱的偏移量。
- 暂停期间音频也要丢，恢复后的音频缓冲用 `CMSampleBufferCreateCopyWithNewTiming` 重编时间戳；视频侧只要有过暂停就走 `CVPixelBuffer` 合成路径（零拷贝直通无法改时间戳），所以 `CIContext` 现在一律创建，不再只在开摄像头时才建。

## 内存与性能账本

先是 1.0.12 那一轮（峰值 / CPU）：

- 🔴 **光标悬停曾是整屏重绘**：遮罩视图里十字线 / 放大镜一开，鼠标每动一下就 `needsDisplay = true`，5K 下一次 750 万像素、一核吃满。现在只开放大镜（不开十字线）时走**局部重绘**：`setNeedsDisplay(旧镜框 ∪ 新镜框 − 8pt)`，十字线要跨全屏没法局部化，那条路保持整画（`RegionSelector` 的 `mouseMoved` / `lastLoupeRect`）。
- **`CIContext` 全应用共享**：马赛克 / 模糊的效果图以前每次都新建 `CIContext`（几十毫秒级 + 一套 GPU 资源），第一次上效果能卡一下。现在 `EffectImages.ciContext` static（OCR 那边早就是 static）。录制引擎里 `ciContext` 本来就常驻（暂停补偿要用），不受影响。
- **截图历史不进内存**：PNG 落盘 + 面板里按需 360px 缩略图解码（`CGImageSourceCreateThumbnailAtIndex`），20 张原图零常驻。
- 选区遮罩的整屏底图（2880×1864×4 ≈ 20.5MB）**不是泄漏**：窗口截图的 SCK 失败兜底要在遮罩收掉之后才裁它。1.0.21 把它的寿命按路径收紧了（见下），但**不能**一律在 finish 里置 nil —— 窗口点选那条路会被裁成空。

然后 1.0.21 这一轮（用户问「内存涨上去不回落，之前的优化是不是无效」之后按实测改的）：

实测先摆在这：空载 12MB；滚动截图拼接峰值 109MB，**1 秒内回落到 43MB**；剩下的 40MB 是 IOSurface 18MB + MALLOC_SMALL 12MB + GPU 1.6MB，而那时三个窗口还挂在屏上——那是"在用"，不是"残留"。录屏峰值只有 16MB，H.264 编码跑在 Apple 的 XPC 进程里，不计入本进程。所以"不回落"主要是分配器蓄水池 + `MADV_FREE` 页 + GPU surface 不还，不是泄漏。

- 🔴 **滚动拼接从 O(N²) 改成 O(N)**：老 `ImageStitch.append` 每拼一帧就 `CGContext` 新开一块整幅位图、把已拼好的图整个重画一遍，第 N 帧复制 N 行。改成 `StitchCanvas`（一块朝下长、按 1.5 倍摊还扩容的画布，每帧只画新增的 offset 行）。旧实现留作**参考实现**，自检拿它跟画布逐像素对照（`坏点 0.0000%`）—— 性能重构必须有人钉住正确性，"跟源页面像"抓不到"少画几行"。
- **预览不再合成整幅**：另开一块 180 宽的低分辨率画布跟着追加，刷新缩略图只 `makeImage` 那一小块。`makeImage` 是整块拷贝，绝不能进每帧路径。
- **横向滚动只转两次**：以前每帧把整幅累积图 `rotate90` → 拼 → `rotateBack`（每帧两次全图旋转）；现在把**每一帧**转 90° 再进画布，收工转一次回来。画布有"方向"概念，用户先横着滚时把已拼的画布搬一次（`realignCanvas`，只搬一次）。
- **效果图按标注框范围生成**：马赛克 / 模糊以前不管涂多小都生成整幅（整屏两张 = 41MB），现在按同类标注的**并集外接矩形**只铺设那一块。滤镜仍在整幅上算（块大小 / 模糊半径的基准不能变），只把这块光栅化。自检钉了两条：裁剪块与整幅同区域逐像素一致；以及用**上黑下白的渐变图**验 y 侧没翻错（纯色图翻不翻都一样，测不出方向错误）。
- **PNG / JPEG 编码走 `CGImageDestination`**：`NSBitmapImageRep(cgImage:)` 会先把整幅拷一份再编码（整屏 20.5MB），`ImageEncode` 与 `Support.copyImageToClipboard` 都改直编。剪贴板那条要转 PNG + TIFF 两种，省的是两份。
- **选区底图按路径放**：`finish(keepBackdrop:)`。拖框确认 / Esc 取消当场放掉 20.5MB（马上要抓同尺寸成图，别叠在一起）；窗口点选必须留着（SCK 查不到窗口时按框裁它兜底）。`--wintest` 实测兜底仍出图：`窗口 999999 已不可截取，改用底图裁剪 1600x2030`。
- **撤销栈 50 步上限**：每步是一整份 `[AnnotationShape]`，编辑一小时能到几百步。

## 窗口截图：窗口在遮罩弹出的一瞬间自己没了

用户报「窗口截图失败：目标窗口已关闭或不可截取」。查下来不是名单对不上（`--wintest` 把
`CGWindowList` 和 `SCShareableContent` 的 windowID 逐个比过，差集为 0），而是**时序**：

Edge 的「扫描 QR 码」这类面板是**瞬态弹窗**，应用一失焦就自己关掉。我们的全屏遮罩为了让键盘
（Esc / 回车 / 方向键）生效必须 `NSApp.activate(ignoringOtherApps:)` —— 一激活，那个窗口就没了；
等到按 `windowID` 去 `SCShareableContent` 查，自然查不到。

三层处理，从"尽量拿到最好的"到"至少别给个死胡同"：

1. `captureWindow` 先按 `onScreenWindowsOnly: true` 查；查不到**放宽到 `false` 再查一次**
   （遮罩把它们盖住时可能被判成"不在屏上"）。
2. 还查不到，就用**遮罩出现之前抓的那张整屏底图**按窗口框裁一块顶上
   （`RegionSelector.cropBackdrop(globalRect:)`）。那张图拍的时候窗口还在，裁出来正是用户
   点选那一刻看到的画面 —— 这比一个错误弹窗有用得多。为此窗口点选模式现在也要抓底图
   （`begin(needBackdrop: true)`），代价是一次 ~130ms 的整屏截图。
3. 两条路都没有才报错。

🔴 坐标换算别想当然：窗口框是**全局左上原点**，底图是**显示器像素**。要先用
`displayBoundsGlobal(displayID).origin` 减掉显示器原点，再乘 `pixelScale`。`--wintest` 会把
裁剪结果落成 `/tmp/boxshot-backdrop-crop.png`，拿 `screencapture -R 同一个框` 一对比就知道对不对。

## 扫码：解不出不是码的问题，是喂进去那张图的问题

「Edge / Chrome 分享 → 二维码」生成的是**圆点模块 + 圆角定位图案**，不是标准方块 QR。Vision 的
`VNDetectBarcodesRequest` 对这类图在候选阶段就容易漏，模块再小一点就直接判空。所以解码不是
"试一次"，是一条回退链（`OCREngine.decodeBarcodes`）：

1. 原图；
2. 放大 2 倍（模块太小；整屏图超过 2600px 就跳过，翻成 6840 宽又慢又没用）；
3. 灰度 + 对比度 ×1.8（JPEG 压过的码边缘发虚）；
4. 灰度图做形态学最大值（膨胀）r=1.5 与 r=3.0 —— **这一步是圆点 QR 的关键**，圆点撑成方块后
   连通域才对得上。

某一次检测抛错不判死（比如当前系统不支持列表里的某个码制），记一笔继续下一张；全都解不出才认输。

比"解不出"更坑的是**解出来了但用户看不见**：

- 🔴 截图浮层的图像面板是 `.floating`(3)、标注工具条是 `.statusBar`(25)，而结果窗是默认的
  `.normal`(0) —— 小区域截图时结果窗正好落在浮层范围内，**被整个盖住**。用户点完「解码」屏幕上
  一点变化都没有，报的就是"扫码功能扫不了"。结果窗抬到 `statusBar + 1`(26)。
- 解不出来时原来弹 `NSAlert.runModal()`，浮层还开着，模态框既可能被挡、又卡住交互。改成开结果窗
  写清楚"没有识别到"，把下一步该干什么一并说清楚。
- 点下去先 `flashStatus("正在识别二维码…")`：整屏图上 Vision 要几百毫秒，中间零反馈，
  用户会认定按钮是坏的。

## 放大镜：先抓底图，再上遮罩

选区时在光标旁常驻一块放大镜（`Capture/Magnifier.swift`），15×15 个源像素放大到 150pt、一格 = 一个像素，下面接 74pt 的信息条：坐标 / 区域 / 色值，色值前带 14×13 的小色块。**按 C 把色值复制走**（显示用 `#64 9E 60` 这种两位一组带空格的写法，复制出去是紧凑的 `#649E60`，两个场景要的东西不一样）。

四个踩过的点：

- 🔴 **顺序：先 `captureDisplay` 抓整屏原图，再建遮罩窗口**。反过来（先 show 再抓）抓到的是已经被自己压暗 28% 的那一屏，色值整体偏暗、拿去做设计全是错的。代价是遮罩晚约 100ms 出现；抓图期间用 `isActive = true` 占位，避免热键连按叠出第二个遮罩。
- **放大镜画在遮罩视图里，不另开窗口**。另开一个透明置顶窗意味着又要处理「非 key 窗口收不到事件 / 落位 / 多屏」一整套问题，而遮罩本来就铺满整屏、本来就在收鼠标事件。代价是每次 `mouseMoved` 都要重绘整屏（放大镜必须跟着光标走），`needsDisplay` 只在开启放大镜时才置位。
- **落位先翻再夹**：默认光标右下 16pt；右边放不下翻左、下边放不下翻上，最后才整体夹进屏幕。夹在翻之后 —— 顺序反了贴边时镜会压住光标。
- **捕捉原点可选**（左上 / 右上 / 左下 / 右下），坐标按用户选的那个角数；默认左下角，照用户给的样张定。

验收不用真去拖选区：`--loupetest` 把放大镜离屏渲染成 PNG。源图刻意做成「顶部一条红、底部一条蓝」，光标压在红条下沿 —— 镜里红条在上就是对的，跑到下面就是翻面了。

## 贴图：文本贴图的文字可选，每张都有置顶按钮

贴图窗是 `NSPanel([.borderless, .nonactivatingPanel])`，默认 `level = .floating`，双击和滚轮交互全在内容视图里。历史落盘在 `~/Library/Application Support/BoxShot/pins/`，索引 `pins.json`，启动时按 `maxPinHistory` 恢复。

1.0.12 起分成两种内容视图，公共部分（拖拽 / 滚轮缩放 / 双击 / 右键菜单 / 置顶按钮）抽到 `PinSurfaceView`：

- **图片贴图** = `PinContentView`，照旧把 `CGImage` 画上去。
- **文本贴图** = `PinTextContentView`：不再把文字当图看，里面是**可选中的 `NSTextView`**（`isEditable = false, isSelectable = true`）。位图仍然保留——「复制图片」和历史落盘还要用它，`PinRecord` 多一个 `text` 字段，恢复时按文字重建文本视图。

两个必须注意的地方：

- 🔴 **文字的拖拽边界**：文字区域整块交给 NSTextView 选字，拖窗口只认四周 12pt 留白；想在文字上直接拖就按住 **⌘**（`PinSelectableTextView` 在 ⌘ 按下时不调 super，改走窗口移动）。选字优先是有意的——不能为了好拖把「可选」做回假的。
- 🔴 **`canBecomeKey` 必须对文本贴图返回 true**：返回 false 的话 NSTextView 拿不到 first responder，字能拖蓝但 **⌘C 复制不走**。图片贴图仍然返回 false（不抢用户正在打字的窗口）。

置顶按钮钉在右上角，**鼠标移进贴图才显示**（常驻会切掉画面一角），点一下在 `.floating` ↔ `.normal` 之间切。按钮是 `FirstMouseButton`（`acceptsFirstMouse` 为 true），否则非 key 窗口里第一下点击会被吞掉，看着像「按钮按不了」。

1.0.11 一次修掉三个：

- **贴图是倒的**：`PinContentView.isFlipped = true`（左上原点、y 向下），在这个坐标系里直接 `ctx.draw(cgImage)` 画出来就是上下颠倒。和截图浮层、滚动拼接一样要走标准配方——先 `translateBy(0, h)` + `scaleBy(1, -1)` 翻回 y 向上的标准空间再画。**这一步必须在镜像（`flippedH`/`flippedV`）之前**，否则"垂直翻转"的含义会跟着反。
- **拖不动**：`mouseDragged` 拿的是**增量** `event.deltaX/deltaY`，却加在 `mouseDown` 记下的原点上（原点之后没更新），于是每帧都把窗口摆回"起点 + 一点点"。改成用**屏幕坐标差**（`NSEvent.mouseLocation` 减按下时的位置）：既不受原点不更新的影响，也不受"窗口自己在动导致 `locationInWindow` 漂移"的影响。另外 `acceptsFirstMouse` 必须返回 true —— 非 key 窗口默认把第一下点击吞掉。
  🔴 顺带一个验证坑：**合成事件（CGEvent）里 `deltaX/deltaY` 恒为 0**，所以靠 delta 的实现无论修没修好都测不出来；换成屏幕坐标差之后 `--pintest` 的 Δy 才等于投出去的 80pt。
- **恢复出来的贴图小一半**：`scale` 的语义是"相对 1:1 的倍数"（`applyScale` 里 `baseW × scale`），初始值却写成 `1/backingScale`（0.5）。窗口一旦被重排（首次缩放 / 从历史恢复）就只剩一半。初始值改 1.0，`PinRecord` 加 `v` 字段（旧记录没有 → 按 1:1 恢复）。

## 快捷键：Carbon，且只提供「整批替换」

`RegisterEventHotKey` 注册系统级热键，签名 `'BSHT'`。API 是 `replaceAll(with:)` 这个形状的，不是 `register()`——早期版本 `register()` 内部先 `unregisterAll()`，注册第二个键时把第一个清掉了，热键静默失效。**这个接口形状让那类 bug 写不出来，别改回去。**

能不能当全局热键有门槛：必须有 ⌘/⌥/⌃，或者无修饰键时必须是 F1–F12。其余无修饰的组合一律拒绝，否则打字时应用会被频繁误触。

读取设置是**严格读取**：设置里没录就是 `nil`，不回退默认值。曾经回退默认值，导致点「清除」之后界面又显示回 F7。

🔴 **录制控件必须自己抢第一响应者**。`NSButton` 默认 `acceptsFirstResponder == false`，点它不会变成
firstResponder，`keyDown` 永远收不到 —— 界面上看着像在等按键，其实键盘事件全被窗口吃了，
这就是「快捷键设置不可用」的根因。现在 `RecorderButton` 覆写 `acceptsFirstResponder` 返回 true，
并在 `mouseDown` 里显式 `window?.makeFirstResponder(self)`（不调 `super`，否则走 momentary 高亮跟踪，
按键还是到不了）。

注册失败必须能被看见：`AppModel.failedShortcuts` 收着被系统拒掉的键位，设置页每行对号入座地标
「要加 ⌘/⌥/⌃，或改用 F1–F12」/「被系统占用，注册失败」。以前只 NSLog，用户录了个纯字母键，
看着"设置成功了"，实际一次都不会触发。

应用内的快捷键（⌘Z / ⌘C / ⌘S / Esc）是 NSEvent local monitor，只在浮层窗口是 key window 时生效，文字输入时不抢。

## 设置面板：三个"看着有效、其实空转"的坑

用户 1.0.9 的原话是「红框那些设置都无效」，查下来是三类不同的问题：

- **面板没观察设置本身**。`SettingsRootView` 只观察 `AppModel`，而设置是另一个 `PreferencesStore`（也是 ObservableObject）。改设置时 model 不发通知，面板就不重绘：勾选框看着回弹、Picker 选完还显示旧值。修法：每页都加 `@ObservedObject var prefs: PreferencesStore` 直接观察设置（快捷键页当初就是因为这个单独加过一次）。
- **「自动保存」没有目录就什么都不做**。原来 `guard prefs.autoSave, let dirPath = prefs.saveDirectory` —— 用户没选过目录时，开关打开了也是空转。现在 `PreferencesStore` 在 autoSave 变 true 且目录为空时当场补成桌面，界面把实际落盘目录显示出来。
- **编码失败静默返回**。`write()` 里 `guard let data = … else { return }`：JPG 编码万一失败，点「保存」什么都不发生也不报错，看着就像"保存格式这个设置没用"。现在会 flash 一句提示。

## Esc 的口径（改过三次，别再改回去）

1.0.6「Esc 退出」→ 1.0.7 改成「只撤选区」→ 1.0.9 用户明确要求「全局按 Esc 强制结束截屏」，恢复成一次到底：

| 阶段 | Esc 的行为 |
| --- | --- |
| 选区遮罩 | `cancel()`：整条流程收掉，不截图、不弹窗 |
| 标注浮层 | 第一次撤掉正在进行的动作（待确认裁剪 / 正在画的那一笔），再按一次关闭浮层（走 `close()`，自动保存开着照常落盘） |
| 滚动截图 | 直接结束，不返回图片 |
| 录制工具条 | 录制中 / 启动中**不响应**（防止误停），停止靠 ✕ 或工具条的停止按钮 |

## 🔴 无边框窗口一个键都收不到（1.0.10 才找到）

用户连着两版报「全局按 Esc 强制结束截屏没生效，截图、窗口截图都没生效」。前两次都在改**判断**（Esc 该退到哪一层、要不要只撤选区），而真正的病根是**按键从来没进过这个进程**：

`NSWindow` / `NSPanel` 的 **`canBecomeKey` 默认是 `false`**（无边框窗口尤其）。窗口不是 key window，`keyDown` 就一个键都收不到 —— `makeKeyAndOrderFront(nil)` 叫了也白叫，`NSApp.keyWindow` 甚至是 nil，而代码看上去两句都在。修法是子类覆写：

```swift
final class KeyableWindow: NSWindow   { override var canBecomeKey: Bool { true }; override var canBecomeMain: Bool { false } }
final class KeyablePanel:  NSPanel    { override var canBecomeKey: Bool { true }; override var canBecomeMain: Bool { false } }
```

选区遮罩、标注浮层、滚动截图的取景框都换成了这两个类。

**还有第二条，顺序不能反**：先 `NSApp.activate(ignoringOtherApps: true)`，再 `makeKeyAndOrderFront` + `makeKey()`。反过来写时应用还没 active，AppKit 会把「become key」推后到激活之后，中间那段时间窗口**看得见但收不到键盘**。

最后再挂一条 `NSEvent.addLocalMonitorForEvents(matching: .keyDown)` 兜住 Esc —— 只要应用收到键盘，就算窗口因为系统原因没拿到焦点也能退出。

### 验证 Esc 要投真键，不能只投自己的队列

`NSApp.postEvent` 只是往**自己的**事件队列里塞一个事件，绕不过窗口服务器，所以它通过并不代表用户按下去也能过。1.0.9 就是被这条骗过去的。真正的等价物是 HID 层投放：

```swift
let src = CGEventSource(stateID: .hidSystemState)
CGEvent(keyboardEventSource: src, virtualKey: 53, keyDown: true)?.post(tap: .cghidEventTap)
```

⚠️ 这需要本进程有辅助功能授权（`AXIsProcessTrusted()`），否则 `post` 是往空气里发、日志里只会看到「没生效」，很容易误判。1.0.10 的实测结论：`AX=true` 时 HID Esc 立刻收掉遮罩；`AX=false` 时同一份代码两条路都失败。


## 提示音：和 BoxPaste 同一套系统音效

八档（Blow / Bottle / Funk / Glass / Hero / Morse / Ping / Purr），中文名照搬 BoxPaste，旁边有「试听」。播放点统一走 `AppModel.playFeedbackSound()`（开关和音效名都在设置里）；录制收尾那条在 `Recorder` 里拿不到 model，改由工具条注入 `finishedSoundName` —— 顺手修掉「关了提示音，录完还是会叮一声」。

### 什么时候才响（用户口径：截完了才响）

"完成"= 这件事有了结果：**OCR 出字、识别码出内容、复制进剪贴板、保存成文件**。

抓下画面本身**不算**完成 —— 以前 `routeCapturedImage` 一开头就响，后面复制/保存再响一次，一张图能叮两声，听着莫名其妙。现在那一声挪到"直接复制"分支里（那条路径确实是完成），其余各控制器（浮层、独立编辑窗、滚动截图、历史面板、录制收尾）各自在自己完成的那一刻响。

存量配置里可能记着已下线的音效名，解码时校验一遍并落回 `Glass`，否则设置页 Picker 会显示空白。

## 箭头：默认工具 + 「不够尖」

打开标注浮层默认就是**箭头**（`EditorDocument.tool = .arrow`，1.0.12）。理由很朴素：截图十次有九次是拿箭头指一下，默认落在别的工具上等于每次都要先点一次工具条。

「箭头不够尖」拆开是两个毛病，都不在"画得细"上：

1. 🔴 **箭杆画到了箭尖**。`lineCap = .round` 会在终点留一个半径 `width/2` 的圆头，尖端永远是个半球 —— 看上去就是钝的。现在箭杆只画到 `尖端 − 头长 × 0.55`，尖端交给填充三角形。
2. **顶点张角 48°（0.42 rad）、头长只有 3.5× 线宽**。现在张角收到 **34.4°（0.30 rad）**、头长 **5.2× 线宽**（下限 16），并且底边中点往尖端内凹 0.78 × 头长 —— 两翼往后掠，是 ▷ 不是 ▲。

几何算在 `EditorRenderer` 里（`arrowHeadLength` / `arrowHeadSpread` / `arrowStemEnd` / `arrowHeadPoints`），**CG 导出渲染和 SwiftUI 实时预览共用同一份**：以前两处各写一遍，改了形状其中一处没跟上，屏幕上和存下来的就不是同一支箭头。

「够不够尖」是主观判断，不能靠看代码下结论 —— `--arrowtest` 把线宽 2 / 4 / 8 的三支箭头离屏渲染成 `/tmp/boxshot-arrow.png`，同时打印头长倍数与顶点张角。

## 摄像头取景框：两套尺寸，别串用

同一个枚举 `CameraBubbleSize` 有两组边长的原因很实在：**画中画和主角不能一样大**。

| 场景 | 属性 | 大 / 中 / 小（pt） | 落位 |
| --- | --- | --- | --- |
| 区域 / 全屏录制的画中画 | `side` | 200 / 150 / 100 | 贴右下角（边距可调，默认 30） |
| 摄像头录制的主角 | `cameraSide` | 680 / 600 / 500 | 固定框正中 |

圆形取直径、圆角矩形取宽度。设置 → 录制 → 质量下面有**三行**：「取景框大小」写 `recordCameraSize`（画中画，默认中 150）、「取景框边距」写 `recordCameraInset`（右下角那条缝，默认 30，范围 0–80，只能靠 stepper 调）、「摄像头录制」写 `cameraRecordSize`（默认大 680）。行尾都把当前点数写出来 —— 尺寸和边距都是绝对值，界面上就该看得到数字，别让人靠肉眼猜大小。

一开始做的是"相对倍数"（跟着选区短边算），用户明确要"我说多大就多大"，于是改成绝对值。只在**实在放不下**时才收，且两套的收缩比不一样（`CameraBubbleController.fittedSide(wanted:anchor:placement:)`）：

```swift
let ratio: CGFloat = (placement == .centered) ? 1.0 : 0.45
return min(wanted, max(96, min(anchor.width, anchor.height) * ratio))
```

`.bottomTrailing` 用 0.45 —— 小窗别挡着内容；`.centered` 用 1.0 —— 主角诉求是"人像要够大"，只要短边装得下就原样落地。固定框 1283×721 里 680 的圆原样落地（721 里只剩 41pt 余量）；画中画塞进 300×200 这种小选区时，200×0.45=90 又要保住 96 的下限，最后落到 96。

### 边距（右下角那条缝）

`CameraBubbleController.position(_:anchor:)` 里画中画那支走纯函数 `bottomTrailingOrigin(anchor:size:inset:)`：

```swift
CGPoint(x: anchor.maxX - size.width - inset, y: anchor.minY + inset)
```

右边和下边吃**同一个** `inset` ——「右下角」就该等距，不给某一侧留特例。`inset` 来自 `Preferences.recordCameraInset`（Int，默认 30，用的时候夹在 0...80），可以在两处调：

- **设置 → 录制 → 取景框边距**：stepper，改完立刻生效（`AppModel.applyPreferenceChanges` → `recordToolbar.applyCameraInset`）。
- **录制工具条 → 选项弹层 → 边距**：只在画中画模式出现（摄像头录制是居中，边距没意义），拖的时候取景框实时跟着挪。

「全屏录制」时 `anchor` 是屏幕的 `visibleFrame`，所以底部那 30pt 是离 Dock 上沿、不是离屏幕物理底边；取景框窗口开了系统阴影（`panel.hasShadow = true`），阴影占掉这 30pt 的一部分，肉眼看着会比 30 更贴边一点。

落位（`CGWindowListCopyWindowInfo`，pt）：录制框 `(214,181) 1283×721`、取景框 `(515,202) 680×680` —— 两者中心 x≈855.5、y≈541.5，**正中对齐**。录制框这组是当场量的；取景框那组是 1.0.24 改成 680 之后按 `position()` 的居中公式算的（`x = 框.midX − 680/2`、`y = 框.midY − 680/2`），改档位时照这条核。

## 摄像头录制：固定录制框 + 录屏（不是"只录摄像头"）

菜单「摄像头录制」在「全屏录制」正下方。它做三件事：摆一个**固定录制框**、框里照常录屏、把摄像头取景框放大后**居中**放进框里。

为什么不是"只录摄像头"：**系统声音只有 ScreenCaptureKit 才有**。1.0.20 先做过一版纯摄像头录制（`AVCaptureVideoDataOutput` → writer），用户试过之后说「我要录制系统声音，那你不如固定一个框出来，加录屏」—— 于是改成框内录屏，音轨问题自然消失，那一版专用引擎/窗口也整体删掉了（不留死代码）。

- **固定框**：`AppModel.fixedRecordFrame(on:)` 取 `visibleFrame` 的 **75%**（用户看第一版说"虚线的那个录制框能不能小一点"，88% → 75%），按 16:9、居中。纯函数，自检盯 16:9 / 居中 / 不出界 / 放得下 680。
  - 🔴 框高必须 ≥ 680，否则 `fittedSide` 会把 680 收下去 —— 本机 1710×1107 → 1282×720（可用区再扣掉菜单栏与 Dock 后 1283×721），只剩 41pt 余量：**谁再把固定框比例往下调（75% → 70% 就只剩 673），680 就会被悄悄收成 673**，自检里那条「固定框放得下 680」就是拦这个的。
- **坐标**：`visibleFrame` 是 AppKit 坐标（左下原点），而 `SCStreamConfiguration.sourceRect` 与虚线段用的是显示器局部坐标（左上原点）。少翻一次 y，录出来的就是屏幕上完全另一块地方 —— 尺寸照样对，只有画面错。`ScreenCapture.displayLocalRect(fromAppKit:displayID:)` 是反函数，自检拿它跟 `globalTopLeftRect` + `appKitFrame` 做来回换算。
- **摄像头**：开框时自动打开取景框（`begin(autoCamera: true)`）。取景框是屏幕上真实的 `.floating` 窗口，落在框里就被 SC 一起拍进成片 —— 所见即所得，编码端不做合成（见上文"摄像头取景框：所见即所得"）。
- **工具条少两个按钮**：这个模式框是固定的，「全屏录制」和「重选区域」都没有意义（用户原话"这两个按钮在这个录制模式下去掉"）。`RecordToolbarController.isCameraMode` 控制是否创建 tag 2 / tag 3，剩下的 ✕ / ● / 暂停 / 麦克风 / 系统声 / 摄像头 / 选项 照旧 —— 计时、音频开关、帧率/格式/质量、暂停恢复全部复用区域录制那一条路，没有第二套。
- 选项弹层同样按模式分流：`RecordOptionsView(model:cameraMode:)` 读写的尺寸项在摄像头模式下是 `cameraRecordSize.cameraSide`，别的一律 `recordCameraSize.side`。串了就会"改了一个、另一个跟着动"。

诊断：`--show-fixedframe`（或 `/tmp/boxshot-fixedframe.trigger`）直接把固定框摆出来看布局。落位日志打两份：`固定录制框 AppKit=… 显示器局部=…`、`取景框落位 框=… 取景框=… → (x,y)`。

## 帧率：8 档，只给 MOV / MP4

`recordFPSOptions = [10, 15, 24, 25, 30, 48, 50, 60]`（放在 `Preferences.swift` 顶层，不放在设置页里 —— `private` 的常量自检够不着，等于没人能验）。24 / 25 是影视与 PAL 的老口径，48 / 50 / 60 给高帧率素材。

引擎两头都能吃下：`minimumFrameInterval` 用 `min(60, fps)`、`AVVideoExpectedSourceFrameRateKey` 用 `max(10, fps)`。

🔴 **码率要封顶**。60fps 是高帧率档新开的组合，「像素 × 帧率 × 0.12」在全屏 5K 上能算出 100 Mbps 以上，编码器直接拒收，录出来是 0 字节。现在 `min(rawBitrate, 80_000_000)`。

## 设置页左对齐：`.frame(width:)` 默认是居中

用户拿红框圈着录制页说"这些元素左对齐一下"。真凶不是间距，是 `.frame(width:)` **默认居中**：每个 Picker 的自然宽度不同，塞进同一个宽度后各自居中，左边缘就各不相同。

现在录制页统一走两个辅助函数 —— `row(标题, 控件, trailing:)`（标签 90pt 右对齐 + 8pt 间距 + 控件 150pt **`alignment: .leading`**）和 `bareRow(控件)`（没有标签的勾选框，左边补 `Color.clear.frame(width: labelWidth)` 占位）。后者是实测出来的：只写 `.padding(.leading, 90)` 会比控件列**左移 8pt**，正是 `HStack(spacing:)` 那一档。

验证方式是量像素而不是看眼睛：截图后逐行扫「第一个非背景像素的 x」，九行必须全落在同一列（本次实测全是 246px @2x）。

## 工具条底色写死深灰 ⇒ 外观也必须写死深色

用户截图反馈「工具条的文字、图标现在都是黑色的」，压在那条 0.13 深灰底上几乎看不见。

真凶不是颜色值写错，是**只固定了一半**：容器底色是 `NSColor(calibratedWhite: 0.13)`（写死），但里面的 `NSImage(systemSymbolName:)` 模板图默认按 `.labelColor` 着色、文字也写的 `.labelColor` —— 系统处于**浅色外观**时这两个都解析成黑色。1.0.20 把毛玻璃 `.hudWindow` 换成实心 NSView 之后这个问题才浮出来（材质那版本身就把前景衬成浅色了）。

修法是**切外观**而不是逐个手写前景色：

```swift
static let toolbarAppearance = NSAppearance(named: .darkAqua)
container.appearance = Self.toolbarAppearance     // 工具条、颜色面板、录制工具条三处都要
```

这样图标、文字、分隔线（`separatorColor`）、禁用态、以后新加的控件全部跟着对，不会漏一个。

但**光切外观还不够**：深色外观下的 `.labelColor` 是"带透明度的白"，图标看起来仍是浅灰（用户第二次拿截图圈着说"这些灰色图标改白色"）。所以图标按钮再显式给 `contentTintColor = Self.toolbarForegroundColor`（纯白），文字标签同理 —— 底色写死就必须前景写死。这个工具条没有禁用态按钮，固定 tint 不会盖掉 disabled 的变灰。

复现/验证别靠肉眼看 app：写个 40 行的离屏渲染脚本，同一套深色底 + 模板图标分别渲染「不指定 tint」与「`.white`」两张 PNG 对比，前者发灰、后者纯白，一眼就分得清。

## 编辑窗口的工具条：宁可滚，不许压（1.0.27）

用户截图："按钮变形了" —— `OCR` 只剩个 `C`、`保存` 剩半个字、`完成` 被挤成 `完`。

根因是**宽度账算不过来**：工具条自然宽度（14 个工具 + 6 色 + 取色器 + 粗细 + 撤销 + 6 个输出按钮）超过 1100pt，而编辑窗口宽度是**按图片自适应**的（`max(640, displayW)`，小图只有 640）。HStack 空间不够时 SwiftUI 的默认行为就是压缩子视图，压的正是 `Label` 里的文字。

三层修法，缺一不可：

1. **外面套一层横向 `ScrollView`**（+ 内层 `HStack.fixedSize(horizontal: true)`）。子视图按自然宽度排，压不动了；窄到放不下就横向滚。按钮永远不会变形。
2. **「完成」钉在 ScrollView 外面**，固定在最右边。它是主操作、唯一带强调色的按钮，跟着一起滚到看不见就等于没有。
3. **6 个色块 + 取色器 + 粗细滑杆收进"颜色圆点"的弹出面板**（`.popover`），跟截图浮层同一个交互（那边是 `colorDotAnchorButton` + `colorPanel` 一套）。这一下省 230pt，1000 宽的窗口里所有按钮都能一行放下，多数时候根本不需要滚。

输出按钮（OCR / 美化 / 贴图 / 保存 / 复制）同时改成**图标 + tooltip**，只有「完成」保留文字 —— 再次省 200pt。

> 顺带一条口径：常驻的「删除」按钮已按用户要求去掉（"不管有没有输文字，这个一直显示"）。删除能力没丢，挪到 `EditorWindowController` 的按键监听里：⌫ / Delete 删选中标注。🔴 那里判断"是不是在打字"必须是 `(firstResponder as? NSTextView)?.window === window` —— 只看类型不够：文字框被 SwiftUI 拆掉后，窗口的 firstResponder 可能还指着那个已经脱离层级的 NSTextView，于是 ⌫ 被当成"在打字"而放行，结果什么都没发生。另外 `CanvasTextEditor.dismantleNSView` 里要把第一响应者还给窗口。

## 文字原地编辑：输入时就是最终效果

用户口径「输入的文字，在输入时就直接显示最终效果，输完确认，之后还可以点击修改」。以前是弹一个
`NSTextField`、按回车才把字画上去 —— 输入时看到的是一行系统输入框，字号/字重/位置都和成图不一样。

现在是把**一个透明的 `NSTextView` 摆在文字落点上**（`OverlayEditor.beginTextEditing`）：字号、颜色、
起点全部来自渲染器那一套（`shape.fontSize * viewPerPixel`、框 = `displayBounds`），打字时屏幕上
看到的就是成图里的样子，输入法候选窗也自然跟着光标走。确认（⏎ / 点别处 / 点工具条）后交给渲染器画，
双击（或文字工具下点已有文字）可以再进去改。

四个必须这么写的地方：

- **打字期间不许走 `commit()`**。每敲一个字压一个撤销点，两行字就能把 50 步的栈刷满，`undoLimit`
  一截断，之前画的标注全从历史里消失。所以拆成 `setLiveText`（只改不压栈）→ `commitEdit(from:)`
  （整段编辑只压一个点）/ `rollback(to:)`（取消）。
- **`textContainerInset = .zero` + `lineFragmentPadding = 0`**。NSTextView 默认带 0/5pt 缩进，
  不关掉的话确认那一瞬间文字会往左上"跳一下"。`--textedit` 就是钉这件事的：打字中与确认后
  两张截图的**黑像素包围盒必须完全一致**（实测 origin/size 偏差 0×0、像素数差 0.0%）。
- **画的时候跳过正在编辑的那一条**（`draw` 里 `filter { $0.id != editingShapeID }`）。两边都画会叠出
  一层更粗更脏的重影，位置差半个像素还发虚。
- **智能替换必须全关**（弯引号 / 破折号 / 拼写纠正 / 文本替换）。截图里写的 `--flag`、`a"b` 是要
  原样进图的，被替换成 `“b` 就不是用户打的那句话了。

### 独立编辑窗口也用同一套（1.0.27）

用户口径：**「编辑工具的输入文字功能跟截图工具条的输入文字功能不一致，也没有调整文字大小的功能」**。
编辑窗口里原来是 `TextField("输入文字，回车确认")` + `.roundedBorder`，固定 240pt 宽、15pt 字号，
跟画布上的字毫无关系；落字时字号写死 `max(22, 30)`，字号控件根本没有。

现在 `CanvasTextEditor`（`NSViewRepresentable` 包 `NSTextView`）把浮层那套配置逐条搬过来：透明背景、
无边框、`systemFont(medium)`、关智能替换、⏎ / Tab 确认、Esc 取消。文字**先挂进 `shapes`**（不压撤销点），
边打边 `setLiveText`，确认时 `commitEdit` 压一个点 —— 跟浮层完全是同一条路。

三个坑：

- 🔴 **抢焦点必须写在 `viewDidMoveToWindow` 里**。第一次实现是在 `makeNSView` 里
  `DispatchQueue.main.async { view.window?.makeFirstResponder(view) }`：那一拍 view 还没挂进 window，
  `window` 是 nil，`makeFirstResponder` 静默失败 —— 实测症状是"点完画布打字一个字都进不去，只留一个空选中框"，
  看着像文字工具坏了。
- 🔴 **Esc 会被编辑窗口自己的 local monitor 先吃掉**（它在 `EditorWindowController` 里无条件
  `performClose`）。必须放行 `window.firstResponder is NSTextView`，让文本视图走 `cancelOperation:`——
  否则用户打一半按 Esc 整个窗口就没了。也别改成判 keyCode 53：输入法组字时的 Esc 是"取消候选"，
  抢掉会把拼音弄丢（浮层那边踩过）。
- **输入时不许把这条文字再画一遍**（`for shape in doc.shapes where shape.id != editingID`）。两边都画会叠出重影：渲染的字和 NSTextView 的字差半个像素，看着像描了一层灰边（用户 1.0.27 截图："输入文字时显示重影"）。浮层那边一直是这么做的。
- **输入框必须挂在 `.overlay` 里，不能当 ZStack 的兄弟视图**。NSTextView 有 `intrinsicContentSize`（宽度跟着文本长），摆在 ZStack 里会参与尺寸计算 → 容器被撑宽 → 画布右边多出一块空白（用户截图红框："一输入文字，布局变形了"）。overlay 不参与父视图布局，位置交给 `offset`，坐标原点跟画布一致。
- **字号与浮层同源**：`EditorDocument.fontSizeOptions` 直接引用 `OverlayEditorController.fontSizeOptions`，
  换算走 `pixelFontSize(points:fitScale:)`（像素 = 点 ÷ fitScale，2x 屏 30pt → 60px，跟浮层
  `fontSize * pixelScale` 同一个口径）。下拉只在**文字工具 / 选中文字**时出现 —— 文字不吃 `lineWidth`，
  把粗细滑杆摆出来既没用也放不下（1080 宽的窗口里工具条本来就排满了）。窗口最小宽度顺带从 520 提到 640。

输出动作的收口在 `renderedImage()` 和 `close()` 里各调一次 `commitTextEditing()` —— 用户打完字
不按回车、直接点保存/复制，最后那行字也得进图。工具切换、改色、改粗细同理，它们走的是**另一个
面板**的点按，不会触发 `contentView.mouseDown`。

## Retina 1x 与「改截图框」的冲突

开了「缩小到 1x 再输出」后，文档是 1x、整屏原图是 2x，两边倍率不同。1.0.7 的处理是直接不允许改尺寸 —— 而且守卫是静默 `return`，用户看到的就是"拖手柄没反应"。现在按 `documentScale = 1/2` 换算：裁剪结果缩到 1x、标注位移乘 0.5，两个功能可以同时开。

### 换图标只换母版

`build-app.sh` 每次都从 `Resources/icon-master.png` 重新生成整套 iconset → icns（同母版同字节，可复现）。所以换图标**只改这一个文件**，别去动 icns：新图先按 macOS 的图标网格处理成 1024×1024、图形 824 居中、四周透明，再覆盖母版。

抠图别用"颜色接近白就透明"—— 这枚图标主体本身就是白色的字母 S，会被抠出洞。做法是从**四角泛洪**只吃掉与边缘连通的白色，再给 alpha 加 0.9px 高斯羽化（JPEG 的硬边直接抠会留一圈白线）。

### 几个不能改坏的约束

- **自检只能跑 `.build` 下的裸产物**，绝不 exec `.app/Contents/MacOS/` 里那个二进制。macOS 26 上那样做会让这个 bundle id 的状态栏登记永久失效，之后图标再也摆不上菜单栏。
- **`LSUIElement` 应用必须程序化建一份最小主菜单**，否则设置页里的文本框按不出 ⌘C/⌘V。
- **动作 `rawValue` 是接口**，写进设置文件里，不要改字符串。
- **保存文件重名自动加 `(2)` `(3)`**，绝不静默覆盖用户文件。
- **写盘失败必须报错**：滚动截图和保存都曾经 `try?` 静默吞错，用户毫无感知。
- **不声明 testTarget**：本机只有 Command Line Tools，声明了会因缺 XCTest 连主程序都编不过。
- **编辑窗口的最小尺寸只能靠 `windowWillResize` 兜**：`contentMinSize` 会被 `NSHostingView` 重算掉，光设它等于没设（见上文 1.0.28）。

## 版本规则与自检

版本号唯一来源是根目录 `VERSION`，打包时按源码指纹（`Package.swift` + `build-app.sh` + `Sources` + `Resources` 全部文件 sha256 后排序再 sha256）决定是否 patch +1。**源码没变就不涨**——版本号在一个只有补丁位的方案里是用掉就回不来的，虚涨不可逆。

自检在 `build-app.sh` 里是硬门禁，不过就 `exit 1` 不产出 `.app`：

```bash
.build/release/BoxShot --selftest
```

## 内存账目怎么读（1.0.23 实测）

「不截图半小时了，内存还是 160」这类问题要分三个数看：**有没有泄漏**、**账面多少**、**真占多少物理内存**。三者不是一回事。

- **没有泄漏**：`leaks -nostacks <pid>` 对跑了 1.5 小时的进程只报 **4 个 leak / 224 字节**（全是 CFData）。
- **账面** = `physical footprint`，也就是活动监视器「内存」那一列。实测 **157.3 MB**（peak 369.8 MB）。
- **真占**：同一时刻 `vmmap -summary` 写的是 `Writable regions: resident=19.0M swapped_out=127.2M` —— 账面里那 127MB 早被系统压进压缩内存/换出，真躺在 RAM 里的只有 19MB，外加一块 57.8MB 的 IOSurface。**「内存上去了不回落」是 footprint 这个指标的本性，不是漏了 free。**

157.3MB 怎么摊开（`footprint -p` 的分类表）：

| 项 | 大小 | 是什么 | 能不能省 |
| --- | --- | --- | --- |
| IOSurface | 57.8MB | 一块 3420×2214 的 `CA Whippet Drawable`（整屏尺寸，RGhA = 8 字节/像素） | 见下，代码层放不掉 |
| MALLOC_SMALL | 58MB | 其中约 47MB 是 **Vision/OCR 的 Espresso 模型**，OCR 过一次就常驻；其余是业务对象 | 不用 OCR 就不会有；框架缓存 |
| MALLOC_LARGE | 11MB | 截图/渲染的大块缓冲 | 关窗会还，malloc 蓄水池留一部分 |
| CoreAnimation + IOAccelerator + graphics + CG raster | ~14MB | 开过窗口就有 | 省不掉 |
| 其它（__DATA / metadata / page table…） | ~16MB | | |

`--memprobe` 逐档实测（全新进程，同一台机器）：

| 档 | footprint |
| --- | --- |
| 启动，还没开过浮层 | 10.7 MB |
| 整屏浮层开着 | 42 MB |
| 关掉 +1.2s（连开三轮都回到这里，不涨） | 22 MB |
| OCR 跑完 +3s | 73 MB（一次性 +47MB，之后不涨） |
| 选区遮罩开着 | 139 MB |
| 取消 +1.5s | 81 MB |
| 真全屏截图：浮层开着 | 157 MB |
| 关掉 +2s | 89 MB |
| 独立编辑窗口（整屏原图）开着 | 167 MB |
| 关掉 +2s | 108 MB（**这里留了 +19MB 不还**） |
| 历史面板 + 空格 QuickLook 预览 + 关面板 | 108 → 116 → 108（净 0） |

**结论**：整屏浮层 / 选区遮罩 / 真全屏截图 / 历史 + 空格预览，关掉后都干净回落；留不下的只有那块 57.8MB 整屏 drawable，而它**不属于任何还活着的窗口** —— `[NSApp windows]` 里六个窗口没有一个是整屏尺寸（最大的是 1606×816 的 `QLPreviewPanel`），外部 `CGWindowList` 看到的也一样。干净进程把所有路径跑一遍，`vmmap | grep Whippet` 是 **0 条**，所以代码里没有对应的强引用可放，最可能是 CoreAnimation 在窗口服务器侧保留的整屏 surface —— 这条**没确证**，留作线索。想让它立刻下去：退出重开；不想管也行，系统在内存压力下自己收。

测的时候踩到的两条：
- 本机 `ps` 受限，量内存只能用 `footprint -p <pid>`（带分类表）和 `vmmap <pid> | grep -i whippet`。
- 独立编辑窗口关掉后那 +19MB，试过在 `windowWillClose` 里把 `contentView` 也摘成 nil，**实测一分没少**，已回退 —— 说明不是我们手里的引用。
